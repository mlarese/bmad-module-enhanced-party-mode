## Le cose che non si indovinano: si applicano
- **Pre-flight, per primo su lavoro nuovo:** `uv run scripts/bmad_context.py {project-root}` → se PRD / architettura / page spec / project context **esistono**, sono vincoli: stack e regole dall'architettura **obbligatori**, perimetro dal PRD, struttura dalle page spec — il seed riempie solo ciò che i documenti lasciano aperto. **Se mancano, non si improvvisa: si producono** (punto sotto, §4.0) — l'analisi autonoma *è* la stesura dei sei documenti, non un lavoro a braccio dichiarato dopo. All'owner arriva un **avviso dichiarativo** prima di partire («nessun documento vincolante: li scrivo io col consiglio — ricerca di dominio e marketing, casi limite, review avversaria; perimetro, stack e testi li decido io; **ti consegno la S1 e mi fermo lì, le altre slice partono quando me lo dici**»): si dice e si prosegue nella stessa risposta, mai «fermami se…». **Le parole del mestiere non si traducono** (`reception` resta `reception`, come `check-in`, `spa`, `booking`): la prova è cosa dice il settore, non la lingua — sta nella ricerca di dominio e sul sito del cliente (§9). **Testi non forniti → si derivano dalla ricerca** (headline, CTA col verbo del dominio, copy di sezione, FAQ, microcopy, `alt`, meta): mai lorem ipsum né gergo da landing generica. **Il lavoro consegnato è finito:** zero `TODO` / «da sostituire» / elenchi di dati fittizi nel file — prezzi, orari e contatti si scrivono verosimili e la loro natura si dice **all'owner in chat**, non nell'artefatto (`craft-rules.md` → *Il lavoro consegnato è finito*). Testi forniti dall'owner o dallo spec → vincolanti, non riscritti. **Senza architettura né project context il canone è legge: SOLID · SoC · KISS · DRY · OWASP · vertical slices.** Disciplina completa: `references/implementation-handoff.md`.
