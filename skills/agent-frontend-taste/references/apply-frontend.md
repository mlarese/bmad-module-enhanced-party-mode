# Apply Frontend

## What Success Looks Like
File FE con assi craft rispettati (vedi `craft-rules.md`); Vera **repeat**; **responsive desktop+mobile**. Fallimento: stub, Inter/purple, mono-`up`, radius 0 implicito, gallery caotica, one-shot non chiesto, palette senza luogo, demo dentro lo skill, **container centrato + tutto left**, **sezioni di tinta piatta dopo la hero**, **clamp degenere min=max**, **solo-desktop / overflow-x / viewport assente**, **lorem ipsum / copy da landing generica quando i testi non erano forniti**, **`TODO` o «da sostituire» nel file consegnato**, **palette e font senza `register` dichiarato**, **scuro strutturale colorato su hero/footer** (croma > 6), **terzo job di fila nello stesso settore di tinta**, **restyle che somiglia al sito vecchio**, **stock generico quando il cliente aveva foto sue**, **servizi inventati quando il sito ne elencava altri**.

## Non-inferables
- **Fase implementativa BMAD (per primo, su new craft):** `uv run scripts/bmad_context.py {project-root}` → se esistono PRD / architettura / page spec sono **vincoli**: stack e regole dall'architettura **obbligatori**, perimetro dal PRD, struttura dalle page spec — il seed riempie solo ciò che i documenti lasciano aperto. Se non esistono (o mancano in parte): **avvisa l'owner prima di partire** — «nessun documento vincolante: procedo in autonomia, ricerca di dominio e marketing, casi limite, review avversaria; perimetro, stack e testi li scelgo io» — poi analisi autonoma **dichiarata nello spec** di accompagnamento (o in chat se non c'è spec), mai dentro la pagina. **Testi non forniti → si derivano dalla ricerca** (headline, CTA col verbo del dominio, copy di sezione, FAQ, microcopy, `alt`, meta): mai lorem ipsum né gergo da landing generica. **Deliverable finito:** zero `TODO` / «da sostituire» / elenchi di dati fittizi nel file — prezzi, orari e contatti si scrivono verosimili e la loro natura si dice **all'owner in chat**, non nell'artefatto (`craft-rules.md` → *Deliverable finito*). Testi forniti dall'owner o dallo spec → vincolanti, non riscritti. Avviso non bloccante ma mai in coda. **Senza architettura né project context il canone è legge: SOLID · SoC · KISS · DRY · OWASP · vertical slices** (dichiarato nell'avviso; scelte non ovvie motivate nello spec). Disciplina completa: `references/implementation-handoff.md`.
- Load `references/craft-rules.md` (nucleo) **+ il file della superficie** (`craft-marketing.md` · `dashboard-rules.md` · `mobile-rules.md`). Soft-gate → skip batch / hero_copy / Vera / espansioni.
- **Sito esistente del cliente:** è fonte di **contenuto** (immagini sue, servizi reali da verificare e riproporre) e **mai** di design — non copiarne layout, palette o hero, nemmeno «per coerenza». Marchio e colori di brand documentati sì, quelli sono vincoli. Vedi `craft-rules.md` → *Il sito esistente del cliente*.
- **Il consiglio valuta gli input** (ricerca dominio+marketing, PRD, architettura, project context, spec consegnati) prima di decidere: chi produce la ricerca non la valida. Documenti sempre vincolanti; buchi e conflitti → assunzione dichiarata + varianza in `docs/varianze/`; ricerca insufficiente → si rifà.
- **Via breve (default su landing e pagine singole):** dopo la ricerca e **prima del codice**, il kernel a 5 campi + `slice_plan` si decidono in **consiglio** (`bmad-party-mode --non-interactive`, goal: decidere perimetro/servizi/flusso/stack/slice — **nessuna domanda all'owner**; il craft non si vota). **Se il lavoro è un progetto con back end e front end** (auth, dati che persistono, back office, API, ruoli): G1 lo dichiara e il consiglio produce prima i **quattro documenti** — PRD · UX/page spec · architettura · `project-context.md` — in **un solo goal**, coi workflow BMAD come stampo e mai invocati uno per uno (`implementation-handoff.md` §4.0). L'esito si **dichiara** in una battuta e non blocca: S1 landing → S2 back office; su app S1 schermata di valore + accesso minimo → S2 auth completa. Il kernel è la **spec madre** in `implementation-artifacts/`; **ogni slice diventa una spec eseguibile** (`bmad-spec` headless, slug `<progetto>-s<N>-<nome>`, Ready for Development, ~900–1600 token sul contratto applicativo — gli assi di craft restano nel DESIGN e si referenziano; le `open_questions[]` si chiudono nello stesso giro) e la sua parte applicativa **la scrivi tu con la disciplina di `bmad-quick-dev`, senza invocarlo** (ha checkpoint in ogni ramo). Se una slice introduce back end reale, **prima** si promuove il ramo e si producono i quattro documenti. Le **varianze** (assunzioni, deviazioni, conflitti risolti, scelte contro un default) vanno in `docs/varianze/`, cinque righe l'una, mai nel deliverable. Vedi `craft-rules.md` → *La via breve* e `implementation-handoff.md` §4.2.
- New/restyle: AW già fatto (o fallo). Owner vuole solo brief → UE.
- **Path:** se non specificato → `{project-root}/frontend-demos/` (+ `anim.css`/`anim.js`). Vietato `skills/agent-frontend-taste/demo/`.
- Applica `hero_copy` da seed se marketing new craft. Se c'è un `hero_archetype` fissato — dalla shortlist `--suggest` o indicato dall'owner — quello vince sul seed: implementa media + placement + panel e rispetta il suo vincolo (`uv run scripts/hero_gallery.py --show <id>`).
- New craft: implementa `grid_system` (≥2 blocchi con `grid-column` esplicito), `alignment_map` (mai mono-allineamento, ≤2 sezioni centrate), misura `ch`, `bleed_rhythm`, `surface_rhythm` con `data-theme` per sezione, una `surface_texture`, `type_voices` (3) + `type_scale` + tracking a due poli. Da `craft_axes.py` se DX non li ha dichiarati.
- **Responsive obbligatorio** (vedi craft-rules): viewport meta, griglie che collassano, no overflow-x, media fluidi, tap target — verifica ~375 e ~1280 prima di chiudere.
- **Approvazione prima di consegnare:** il consiglio (`bmad-party-mode --non-interactive`) approva se il deliverable soddisfa **tutte** le richieste dei documenti vincolanti + craft-rules; il rifiuto deve nominare la richiesta mancante, il gusto non è un veto. **Massimo cinque rifiuti** (la stessa richiesta non ne motiva due): al quinto si consegna dichiarando cosa resta scoperto, come varianza. Sostituisce la review avversaria, non si aggiunge.
- Dopo statico sostanziale: invoca Vera (`repeat: always`, `motion_seed`, `motion_techniques`, mappa direzioni).
- **Verifica il colore, non fidarti del nome che gli hai dato:** `uv run scripts/palette_guard.py --check <file> --last <da MEMORY last_hue_sectors>` — settore dominante per area e croma dello scuro. Violazioni → correggi prima di consegnare.
- Chiudi: path file + brand-test + **check responsive (~375 e ~1280)** + **palette_guard pulito** (+ light/dark se dashboard). Aggiorna MEMORY `last_*` (inclusi `last_hue_sectors` e `last_ink_families`).
